## Unit-number constraints

[Spec 008 G11](../008-nic-unit-numbers/spec.md) requires exact-only matching for numbered interfaces and a numbered-first claim pass. It explicitly defers edit-in-place and live hardware convergence, and its task T032 (vmop-4092) commits to this follow-on: live add, live application of admitted renumbering, and a device-preserving Edit for numbered interfaces. Its MAC-coherence warning applies directly: an edit must never combine a new provider attachment ID with a MAC inherited from a different provider-pinned interface. T032 also lists adapter-type support as a separate follow-on. This draft initially kept it out of scope; the feature owner's 2026-10-27 decision includes it here using Remove+Add. The evidence and adopted contract are recorded below.

The [existing platform research](../008-nic-unit-numbers/research.md) reports explicit unit-number hot-add in E15 and same-slot removal/addition in E06 on its recorded vCenter/ESX builds. It also reports key reuse after replacement. This is useful evidence for those testbed cases, not a supported matrix for all NIC types, guest OSes, providers, or live edits. Tests must not equate unchanged device key with absence of replacement.

## Platform API references

- `VirtualDeviceOption.plugAndPlay` describes hot-add capability, while `hotRemoveSupported` describes hot-remove capability. This provides separate eligibility inputs, not a complete live-edit policy. [VirtualDeviceOption](https://developer.broadcom.com/xapis/vsphere-web-services-api/latest/vim.vm.device.VirtualDeviceOption.html)
- `GuestOsDescriptor.supportsHotPlugPCI` reports whether the configured guest OS supports PCI hot plug. It comes from the same `QueryConfigOption` result as the device options and is the guest-side input to R1. The pinned govmomi exposes it as `SupportsHotPlugPCI`. The existing `pkg/providers/vsphere/environment_browser.go:QueryConfigOptionEx` returns both, but it lives in the root provider package, which `session` and `network` cannot import.
- `VirtualDeviceConnectInfo.connected` is meaningful while running; `startConnected` controls connection on startup, and `allowGuestControl` controls guest connection control. The pending-replacement policy must account for all applicable fields. [VirtualDeviceConnectInfo](https://developer.broadcom.com/xapis/vsphere-web-services-api/latest/vim.vm.device.VirtualDevice.ConnectInfo.html)
- `GuestNicInfo` documents device identity and guest configuration fields without a per-interface report timestamp. `GuestInfo.toolsRunningStatus` describes Tools availability, not the age of a NIC report. No freshness guarantee can be inferred from rereading these cached properties. [GuestNicInfo](https://developer.broadcom.com/xapis/vsphere-web-services-api/latest/vim.vm.GuestInfo.NicInfo.html), [GuestInfo](https://developer.broadcom.com/xapis/vsphere-web-services-api/latest/vim.vm.GuestInfo.html)
- The Ethernet-card API explicitly uses an empty external ID to unset it and permits the platform to override Generated/Assigned MACs. The subnet-ID description does not establish the same unset behavior. [VirtualEthernetCard](https://developer.broadcom.com/xapis/vsphere-web-services-api/latest/vim.vm.device.VirtualEthernetCard.html)
- DV port connection cookies are server-generated; a portgroup target need not pin a port, and binding rules constrain when a port key may be supplied. [DistributedVirtualSwitchPortConnection](https://developer.broadcom.com/xapis/vsphere-web-services-api/latest/vim.dvs.PortConnection.html)
- Device configuration expects necessary complete device properties. ConfigSpec supports a changeVersion guard. ReconfigVM applies the submitted configuration atomically; this does not include provider CR changes or make client timeouts definitive. [VirtualDeviceConfigSpec](https://developer.broadcom.com/xapis/vsphere-web-services-api/latest/vim.vm.device.VirtualDeviceSpec.html), [ConfigSpec](https://developer.broadcom.com/xapis/vsphere-web-services-api/latest/vim.vm.ConfigSpec.html), [ReconfigVM_Task](https://developer.broadcom.com/xapis/vsphere-web-services-api/latest/vim.VirtualMachine.html#reconfigure)
- `ResetGuestInformation` clears the VM's guest cache only while powered off and requires `VirtualMachine.Config.ResetGuestInfo`. This is an offline recovery candidate, not permission to power-cycle automatically or evidence of live report freshness. [ResetGuestInformation](https://developer.broadcom.com/xapis/vsphere-web-services-api/latest/vim.VirtualMachine.html#resetGuestInformation)
- **Flexible guest customization (Q10).** vSphere API 9.1 adds network-only customization of a running guest. Findings:
  - **Types.** The pinned govmomi has `CustomizationLinuxFlexPrep` and `CustomizationWindowsFlexPrep`, both `minAPIVersionForType` 9.1.0.0. They take the place of `LinuxPrep`/`Sysprep` in `CustomizationSpec.Identity` and carry no identity settings in 9.1. API 9.1 also adds `CustomizationDisableIpV4`.
  - **Methods.** The spec is applied with `VirtualMachineGuestCustomizationManager.CustomizeGuest_Task`, reached through `ServiceContent.guestCustomizationManager`. Linux guests also need `StartGuestNetwork_Task`. `AbortCustomization_Task` releases the engine lock after a failed step, and the guest network may then be inconsistent.
  - **Credentials.** All three request types carry a required `auth BaseGuestAuthentication` (no `omitempty`). VM Operator holds no guest credentials and never calls guest-operations APIs today, so this is the adoption blocker.
  - **Scope.** Only IP address, gateway, and DNS for one or more NICs. Adapters are selected by MAC in `nicSettingMap` or by PCI order. Windows supports per-NIC DNS; Linux DNS is global.
  - **Requirements.** The VM must be running with `toolsd` available. The documented guests are RHEL 6.8+/7.4+, CentOS 7.4+, SLES 11 SP4/12 SP3+, Ubuntu 16.04+, Windows 7+, and Windows Server 2008 R2+. The recovery page says the procedure tolerates vMotion.
  - **Not documented.** Whether a reboot is needed; whether NICs omitted from `nicSettingMap` are left untouched; how much `StartGuestNetwork_Task` disrupts other NICs; whether `CustomizeVM_Task` accepts a FlexPrep identity on a powered-off VM; how it interacts with a concurrent `ReconfigVM_Task`; and whether a Cloud-Init-managed guest tolerates it.
  - **Test support.** The pinned vcsim has no `GuestCustomizationManager` handlers, so tests need a provider-level seam or a custom simulator handler.
  - **Sources.** [Flexible customization for running VMs](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/administration-sdks-cli-and-tools/introduction-to-the-vcf-programming-guide/the-vsphere-web-services-sdk/virtual-machine-guest-operations/flexible-customization-for-running-virtual-machines.html), [Customizing the guest with a flexible spec](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/administration-sdks-cli-and-tools/introduction-to-the-vcf-programming-guide/the-vsphere-web-services-sdk/virtual-machine-guest-operations/flexible-customization-for-running-virtual-machines/customing-the-guest-with-flexible-customization-spec.html), [Restarting the guest network](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/administration-sdks-cli-and-tools/introduction-to-the-vcf-programming-guide/the-vsphere-web-services-sdk/virtual-machine-guest-operations/flexible-customization-for-running-virtual-machines/restarting-the-guest-network.html), [Recovering from customization errors](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/administration-sdks-cli-and-tools/introduction-to-the-vcf-programming-guide/the-vsphere-web-services-sdk/virtual-machine-guest-operations/flexible-customization-for-running-virtual-machines/recovering-from-guest-customization-errors.html).

## Local serialization experiment

Ran a temporary Go program using the repository's pinned govmomi `v0.57.0-alpha.0.0.20260930024634-9b65cf3964d3`. It created a `VirtualVmxnet3` with a connected `Connectable`, nonempty external/subnet IDs, copied it with `types.DeepCopy[types.BaseVirtualDevice]`, assigned empty IDs and `Connected=false` on the copy, then marshaled a ConfigSpec containing the Edit with `vim25/xml.Marshal`.

```text
concrete_copy_type=*types.VirtualVmxnet3
original_connection_preserved=true
external_id_element_present=false
subnet_id_element_present=false
connected_false_on_wire=true
```

This verifies copy isolation for the exercised nested pointer and wire omission of empty IDs. Two further facts from the pinned source: `types.DeepCopy` round-trips through the JSON codec, so empty `omitempty` slices and maps come back nil and must not be treated as a semantic change; and `SubnetId` carries `vim:"9.0.0.0"`, so it is serialized only for sessions negotiated at that API version or later. `VirtualDeviceConnectInfo.Connected`, `StartConnected`, and `AllowGuestControl` are not `omitempty`, so every Edit of a card with a non-nil `Connectable` restates all three; an Edit built from observed state therefore re-asserts the observed runtime connection. It does not prove how any vCenter treats omitted subnet IDs, establish a working explicit-empty serializer, or validate platform live edits. The complete request serializer and server read-back remain required implementation tests.

## Adapter-type changes (2026-10-27)

**Decision:** The feature owner accepted Remove+Add for adapter-type changes on 2026-10-27, noting these changes should be uncommon. Use it both powered off and for supported live transitions; do not implement or require further comparison with type-changing Edit. The available evidence does not establish that SOAP `ReconfigVM` universally prohibits changing a concrete NIC type through Edit, nor does it establish supported live type-changing Edit behavior on the target platform. No real-vCenter experiment was available for this investigation.

| Evidence | What it establishes |
|---|---|
| VMware's [Terraform provider NIC update implementation](https://github.com/vmware/terraform-provider-vsphere/blob/main/vsphere/internal/virtualdevice/virtual_machine_network_interface_subresource.go), `NetworkInterfaceSubresource.Update` | An `adapter_type` change creates the requested concrete card with a temporary negative key and returns Remove followed by Add in the same device-change list. Ordinary updates use Edit. This is an implementation precedent, not proof that Edit is forbidden by the API. |
| [Original SOAP conversion example and reported success](https://community.broadcom.com/vmware-cloud-foundation/discussion/wrong-network-adapter-created-by-new-vm) | A 2008 example submits a `VirtualPCNet32` with the existing `VirtualVmxnet` key and operation Edit through `ReconfigVM`. This contradicts a blanket claim that concrete type conversion can never use Edit, but does not validate modern VMXNET3/E1000e conversions or hot-plug. |
| [Firsthand PowerCLI conversion reports](https://community.broadcom.com/vmware-cloud-foundation/discussion/what-is-doing-set-networkadapter-cmdlet) | Historical E1000-to-VMXNET3 changes could appear successful in VM configuration while the running guest still saw E1000; powered-off conversion was recognized on startup. These reports do not expose the SOAP operation. They require us to verify guest-visible replacement, not only task success or config read-back. |
| Broadcom's [E1000e-to-VMXNET3 procedure](https://knowledge.broadcom.com/external/article/457367/procedure-to-change-virtual-network-adap.html) | The documented vSphere Client procedure shuts down the VM, removes the old adapter, adds the requested type, and configures the new guest interface. It establishes a documented offline replacement path, not a live support guarantee. |

The pinned govmomi `EditDevice` helper merely submits the provided device with operation Edit. Vcsim replaces its stored device during Edit without establishing real-host type-transition support. Neither is sufficient evidence for enabling this operation.

**Planned handling:** G16 and AC24–AC25 replace the draft's adapter-type exclusion and non-default-type deferral. `Policy.AdapterTypes` gates explicit-type create/add and replacement. Match hardware by the existing identity rules first, including exact unit-number matching, then compare the explicit desired concrete type with the observed type. A mismatch is a replacement of that matched adapter; type must not become another identity selector or cause fallback to a different unit. An omitted type preserves existing matched/class/image hardware and otherwise defaults to VMXNet3 for a new interface.

Construct a fresh destination-type device and submit Remove+Add in one reconfigure at the same unit number. Apply the ready provider attachment, its MAC policy, the agreed connection defaults, and only tuning supported by the destination type. Do not copy subtype-specific fields blindly. A type-only change must not by itself allocate a replacement provider CR; if the attachment also changes, use the existing readiness and disconnect/reconnect contract. Preserve the existing card until the pair is eligible, and defer with an actionable reason when live replacement is unsupported. Observe actual type, key, and MAC afterward, invalidate prior guest data, and verify a subsequent pass is a no-op. R14 must validate each supported pair before live activation; retaining an explicit offline path does not authorize the operator to power-cycle a VM.

## Required experiments

Record VM hardware/guest versions, actual card subtype, provider/backing, host and vCenter versions, capability inputs, exact requested ConfigSpec, fault/task results, and before/after hardware. Use disposable test VMs. Vcsim is not evidence of live platform support.

1. **R1 / Q2**: Hot-add and hot-remove each supported card/provider combination; include denied support and runtime restrictions. Verify capability lookup against actual acceptance and guest observation.
2. **R2 / Q2**: Edit backing, external ID, and provider-pinned MAC together while on/off. Cover generated-to-generated, pinned-to-pinned, pinned-to-generated, and generated-to-pinned transitions. Verify destination-port/MAC coherence, generated-address preservation where permitted, and idempotence.
3. **R3 / Q2**: Disconnect a pending replacement while retaining its backing, prevent guest reconnection, restart the operator, then apply the ready provider CR's attachment and reconnect in the same reconfigure. Check `Connected=true` while running, `StartConnected=true`, and `AllowGuestControl=true`, including an adapter disconnected before replacement. Verify cancellation revalidates its target, task failure does not reconnect to the old attachment, and a later guest disconnect after completion causes no reconnect loop. No previous connection settings are saved.
4. **R4 / Q3**: Try a disconnected `VirtualEthernetCardNetworkBackingInfo` placeholder with no unintended real attachment across supported backing types/power states. Determine whether it releases the old provider port and whether reverting to the real backing preserves identity. Optional; do not enable it on assumption.
5. **R5 / Q2**: Replace at the same unit number while running, including pair rejection. Observe actual MAC/key results and verify no cleanup follows a failed or uncertain task.
6. **R6 / Q5**: Add two unnumbered, generated-MAC NICs to the same backing; interrupt after reconfiguration and restart before MAC observation. Establish whether provider identity can distinguish them durably. If not, require unit numbers for this case or design explicit persistence before enabling it.
7. **R7**: Fail or time out reconfiguration, delete/recreate CRs with the same names, rapidly change desired networks, and revert a snapshot. Verify reconstruction from observed state, correct UID deletion preconditions, and no stale power-on authorization.
8. **R8 / Q7**: Change attachment while preserving key/MAC and initially preserving the guest IP report. Record guest-property changes, Tools state, task ordering, and any available refresh/acknowledgment evidence. Test same-IP recovery, delayed mixed reports, guest MAC overrides, and no Tools. Determine exactly which signal establishes acceptable post-change data; do not equate a poll timestamp or arbitrary timeout with freshness.
9. **R9 / Q7**: Crash between invalidation persistence, reconfigure, and status publication; repeat with failed/uncertain tasks, snapshot revert, and out-of-band NIC changes. Prove restart preserves uncertainty and does not indefinitely invalidate unchanged attachments. Validate active primary-IP withdrawal/recovery through Service endpoints and default probes.
10. **R10 / Q2**: Capture full SOAP requests for explicit ExternalId clear, subnet-ID reset behavior, Generated/Assigned preservation and manual-to-managed generation. Verify each concrete card's `xsi:type`, full configuration, platform read-back, and subsequent no-op. Cover same-backing external-ID change without accidental port rebind.
11. **R11 / Q8**: Exercise allocation overlap, same-network replacement, legacy CR names, Subnet/SubnetSet name collisions, A→B→A cancellation, and A→B→C supersession for every provider. Record when old allocations can be released, especially when hardware has no per-CR identity or guest IPAM still uses the old allocation.
12. **R12 / Q7**: Validate powered-off cache reset, cleared-data observation, next-boot report recovery, same-IP and changed-IP cases, missing privileges, crash between steps, and VM-wide effects. Verify cloud-init cached primary hints cannot undo invalidation and that guest validity does not block power-on. This gives Q7 a concrete offline recovery path while the live signal is investigated.
13. **R13 / Q10**: Optional. On API 9.1, apply a `LinuxFlexPrep` and a `WindowsFlexPrep` spec to running guests after a hot-add and after an attachment edit. Find out:
    - which `GuestAuthentication` forms vCenter accepts, and whether any of them avoids per-VM guest credentials;
    - whether NICs omitted from `nicSettingMap` are left untouched;
    - how far `StartGuestNetwork_Task` disrupts other NICs;
    - abort and retry behavior, and interaction with a concurrent reconfigure;
    - behavior on a Cloud-Init-managed guest;
    - whether a powered-off `CustomizeVM_Task` accepts the FlexPrep identity.

    Without a credential model that needs no user secrets, record Q10 as not adopted.

14. **R14 / Q2**: Validate a single Remove+Add reconfigure at the same unit for concrete type changes in both directions for VMXNET3/E1000e and each additional supported type, powered off and powered on. Type-changing Edit comparison is not required. Capture the SOAP concrete type, task outcome, hardware read-back, and actual guest PCI device/driver before any reboot or power cycle. Cover destination-incompatible tuning/UPT fields, generated and pinned MACs, simultaneous attachment change, pending provider readiness, failure/uncertain completion, operator restart, and subsequent no-op. Record supported pairs separately from merely accepted requests; neither a config-only type change nor a vcsim result proves live replacement.

## Draft decisions

Keep old backing plus disconnection as the baseline; make placeholder backing optional. Use explicit readiness data rather than conditions for control flow.
