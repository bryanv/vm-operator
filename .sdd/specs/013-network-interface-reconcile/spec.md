# Feature Specification: Network Interface Reconciliation and Hot Plug

- **Feature branch**: [`bryanv/network-interface-hotplug-plan`](https://github.com/bryanv/vm-operator/tree/bryanv/network-interface-hotplug-plan)
  - **Fork**: `bryanv/vm-operator`
  - **PR target**: `vmware-tanzu/vm-operator`
- **Created**: 2026-10-18
- **Status**: Draft
- **Epic**: vmop-4418
- **Related work**: [NIC unit numbers](../008-nic-unit-numbers/spec.md), vmop-3982 — this spec is the powered-on and edit-in-place follow-on that spec 008 task T032 (vmop-4092) commits to; [device and bootstrap separation](../004-remove-network-interface-result/plan.md), vmop-3999

Existing VMs need to reconcile each network interface independently, preserve existing adapters when a network attachment is replaced, and apply supported changes while running. An interface awaiting its network provider must be visible as pending without preventing unrelated VM work.

Today a single pending interface stops the rest of an existing VM's update, including a requested power-off. Interfaces without a VMware Tools report have no status entry. Network changes apply only while the VM is powered off.

## Relationship to the NIC unit-number contract

Spec 008's API fields have shipped in `v1alpha6`. Their published documentation describes behavior that this feature intentionally changes when it is enabled:

- Re-pointing a numbered interface at a different network edits its existing adapter in place where supported, keeping its unit number, device key, and (where valid) its MAC. Spec 008 currently documents this as a device replacement with a new key and MAC (spec 008 G12, acceptance criterion 7, and the `unitNumber` field documentation).
- Every desired interface has a status entry whether or not VMware Tools reports it. Spec 008 G2 and the status `unitNumber` documentation currently describe Tools-only entries.
- Admitted interface additions and removals apply while powered on where supported. Spec 008 defers them to the next power-off (spec 008 G13 and its non-goals).

Unit-number identity itself (exclusive exact matching, assignment, backfill, and admission) is unchanged. The published field documentation must describe the behavior of both the feature-enabled and feature-disabled paths before this feature is enabled.

## Delivery and gating

The feature has two parts with different gating:

- **Ungated restructuring.** The rework of how existing VMs observe, match, plan, and apply network interfaces ships without a gate and replaces the current implementation. It preserves today's observable behavior, with two deliberate fixes: a pending interface no longer blocks shutdown or unrelated VM work (G2), and unused provider resources are retired safely and retried (G8).
- **Capability-gated behavior.** A Supervisor capability enables the new user-visible contracts: live interface changes (G1), in-place attachment edits and pending-replacement disconnects (G3, G4), the escape hatch (G9), per-interface status (G11, G12), adapter-type support (G16), and the bootstrap rule (G15). These are the behaviors that revise spec 008's published contract (see above). With the capability absent, network changes to a running VM wait for power-off as they do today, and that wait is now reported. VPC restore remains the one exception: as today, it updates a running VM's adapter in place.

## Goals

- **G1 MUST**: Add and remove interfaces on a powered-on VM when the platform and that VM support the requested operation. Unsupported live operations remain pending until the VM is powered off; the operator does not power-cycle the VM automatically.
- **G2 MUST**: Continue independent reconciliation for an existing VM when an interface is pending. Block bootstrap customization and transitions from powered off to powered on until required network prerequisites and hardware configuration are observed ready. Allow requested shutdown and suspend while networking is pending. Resuming a suspended VM is not blocked, because a suspended VM cannot be reconfigured; its pending changes then follow the running-VM rules.
- **G3 MUST**: When the attachment for an existing logical interface is replaced without a requested adapter-type change, preserve its adapter using an in-place edit where supported. Preserve adapter type and placement, and preserve a generated MAC when valid for the new attachment. A change in a provider-pinned MAC must apply the new MAC coherently with its attachment identity. A simultaneous type change follows G16.
- **G4 MUST**: If a replacement attachment is pending, retain and disconnect the identified existing adapter when supported, including disabling connection at the next power-on and guest reconnection. Once the desired provider resource is ready, automatically reconnect the adapter in the same reconfigure that applies its new attachment; while powered off, enable connection at the next power-on. Reconnection does not depend on saved pre-replacement connection settings. An unsupported or failed disconnect must report the actual connection state and required action. A temporary readiness failure of an unchanged attachment alone must not disconnect a working adapter. An unresolved mapping must not cause removal of a possibly still-required adapter.
- **G5 MUST**: Support NetOP/VDS, NCP/NSX-T, VPC, per-namespace provider selection, and the named-network test path. A provider need not supply a MAC before adapter creation; customization uses the MAC observed after vSphere configures the adapter.
- **G6 MUST**: Preserve the NIC unit-number feature's exclusive hardware identity semantics when enabled. A numbered interface with no adapter at its number stays unmatched; it never claims another adapter by backing, MAC, or array position. Unnumbered interfaces retain a supported compatibility path.
- **G7 MUST**: Report pending interface names and actionable reasons through VM conditions. Keep observed network status distinct from desired guest configuration. Neither a successful task submission nor provider readiness alone means hardware is converged.
- **G8 MUST**: Retain an old provider resource until hardware no longer uses its attachment. Cleanup must survive retries, operator restart, failed reconfiguration, and deletion/recreation of a provider object with the same name.
- **G9 SHOULD**: Provide an internal, undocumented escape hatch to replace an adapter instead of editing it when an attachment changes. It must obey readiness and live-operation restrictions and must not cause replacement on every reconcile.
- **G10 MUST**: With the capability absent, keep existing behavior apart from the G2 and G8 fixes. Preserve create-path prerequisites and deliver cluster-observable behavior with E2E coverage. The existing attachment changes that do not require mutable networks — fail-over network re-pointing and VPC restore — use the restructured path regardless of the capability and follow the same contracts as user-requested changes.
- **G11 MUST**: Expose status and conditions for every desired interface, including interfaces whose provider or virtual adapter does not yet exist. Distinguish provider readiness, applied hardware, and guest information. Absence of guest information must not prevent hardware readiness, bootstrap, or initial power-on.
- **G12 MUST**: Reject guest network reports that conflict with current adapter identity, and invalidate guest information when an attachment changes. Stale or unverified addresses must not be advertised as current primary addresses or make guest synchronization appear successful. Lack of freshness evidence must be represented explicitly; reading the same cached value again does not make it fresh.
- **G13 MUST**: Pending/error feedback identifies the affected interface, target provider resource/network, actual connection state, and whether the user should wait, fix a resource, configure the guest, or request shutdown. Removal and resource-cleanup work remain visible after an interface leaves the spec. Report transition Events without flooding unchanged reconciles.
- **G14 MUST**: An attachment replacement preserves unrelated adapter settings, connects the ready attachment per G4, clears obsolete provider identity correctly, and survives cancellation, superseding edits, operator restart, and concurrent VM updates. Each supported replacement scenario has a tested completion or explicit recovery path.
- **G15 MUST**: With the capability enabled, a network-interface change does not by itself re-run LinuxPrep or Sysprep customization at the next start. This covers an addition, a removal, an attachment edit or replacement, an adapter-type change, and a change to an existing interface's declared guest addressing, whether live or powered off. A change to any other customization input keeps today's behavior, and that customization then applies the current network settings. Enabling the capability on an existing VM does not by itself trigger customization. Cloud-Init guest data keeps its current update behavior.
- **G16 MUST**: Honor an explicit interface `type` for supported devices. Match hardware independently of type, then replace a matched adapter whose concrete type differs using Remove+Add in one reconfigure at the same unit number. Never use Edit to convert type or require the attachment-replacement escape hatch. Build the destination type with the ready provider attachment and compatible settings; retain the old adapter until the complete pair is eligible. A type-only change does not allocate or retire a provider CR. An omitted type preserves a matched adapter's type; a new interface without an existing class/image adapter defaults to VMXNet3. Unsupported types or transitions are reported without substituting another type. Apply the same type-selection rules on create, powered-off update, and eligible live update; type changes invalidate prior guest data even if key and MAC are reused.

## Non-goals

- Replay first-boot customization to configure a newly added or changed guest interface (G15). Guest operating-system configuration of that interface is left to the guest, unless Q10 adopts a network-only customization mechanism.
- Change NIC unit-number assignment, backfill, admission, or old-version conversion contracts.
- Add per-interface Connected/StartConnected spec fields or preserve historical connection settings across an attachment replacement. Such spec fields are future work; this feature automatically connects a ready replacement and does not continually reconnect a converged adapter after a later guest disconnect.
- Convert adapter type using Edit, infer a type change from a backing change, or guarantee support for every type in the API enum. G16 uses Remove+Add only for explicit type mismatches; device/provider/platform eligibility still applies.
- Treat an unvalidated placeholder backing as a prerequisite for the baseline implementation.
- Guarantee exact guest-report age without a source that supplies freshness evidence. The feature distinguishes contradictory, unavailable, and unverified information and does not invent report timestamps.

## User stories and acceptance criteria

### US1 Running VM changes

Persona: DevOps user operating a running VM.

1. **AC1**: Given a running VM and supported adapter, adding a ready interface creates exactly one adapter without a power transition. Removing that interface removes its adapter; other adapters keep their identity and configuration. Repeated reconciliation performs no further change.
2. **AC2**: Given an unsupported live operation, the VM remains running, its condition names the deferred interface and explains that power-off is required, and independent supported work proceeds. After a user-requested shutdown, the pending change converges.
3. **AC3**: Given a pending new interface, unrelated VM updates and ready interface changes continue, and a requested shutdown succeeds. The pending interface does not disappear from readiness reporting or cause deletion of another adapter or desired provider resource.

### US2 Replacement attachments

Persona: DevOps user re-pointing an interface; CSP admin operating the network provider that owns the old and new allocations.

4. **AC4**: Given an existing logical interface whose network attachment is replaced, a supported edit preserves adapter type and placement and a valid generated MAC. A provider-pinned MAC and attachment identifier both match the new provider resource afterward. Reconciliation is subsequently a no-op.
5. **AC5**: Given a pending replacement with a known existing adapter and supported disconnect, the adapter is retained and disconnected. It cannot reconnect on the next start or through guest control. Once the new attachment is ready, the same reconfigure updates the adapter to that attachment and reconnects it, enables connection at the next power-on, and re-enables guest connection control. This also applies if the adapter was disconnected before replacement; no previous connection settings are restored. A ready replacement needs no separate reconnect task. Unsupported/failed operations report actual state and required action. An unchanged attachment becoming temporarily unready does not trigger disconnection, and a later guest disconnect after a completed replacement does not trigger continuous reconnects.
6. **AC6**: Given the replacement escape hatch, a real attachment change produces one removal and one addition when permitted. Leaving the annotation present does not churn a converged adapter. An unsupported replacement remains pending without removing only half of the pair.
7. **AC7**: Given failed, uncertain, or interrupted reconfiguration, old provider resources remain while their attachments are still used. After successful hardware observation, cleanup retries safely and does not delete a newer object that reused the old name.

### US3 Readiness and provider compatibility

Persona: DevOps user waiting on networking; partner engineer (for example VKS or CCI/VCFA UI) consuming per-interface status, primary IPs, and conditions.

8. **AC8**: Given an existing powered-off VM with an unready interface or unapplied network changes, bootstrap customization and power-on wait while independent reconciliation continues. Once current hardware and required MACs are observed, those actions can proceed. A new VM continues to wait for provider prerequisites before creation.
9. **AC9**: Given a provider that supplies no MAC, creation or hot-add succeeds without inventing a manual MAC. Status and applicable bootstrap data later use the vSphere-assigned MAC for the correct interface, including multiple interfaces on the same network. Unknown or ambiguous identity remains pending rather than assigning another interface's MAC.
10. **AC10**: Given numbered, unnumbered, and mixed interfaces, device reconciliation, status, network boot order, and NIC tuning agree about which hardware belongs to each interface. Reordering the spec list does not change numbered interface identity. An exact-number miss never falls back.
11. **AC11**: Given a provider read failure, a paused or suspended VM, a running task, a snapshot revert, or an operator restart, networking honors existing lifecycle restrictions and rebuilds its observations before acting. A missing readiness result cannot accidentally permit power-on.
12. **AC12**: Given any supported provider or feature-flag combination, behavior with the capability absent remains compatible apart from the G2 and G8 fixes. Capability-enabled create, powered-off resize, off-to-on, and powered-on paths obey the same network identity and readiness contracts.
13. **AC13**: Given a newly desired interface, status immediately contains its name and per-interface conditions even before its provider resource or adapter exists. Hardware identity and guest IP data are absent until observed; provider readiness alone does not imply that the adapter was added.
14. **AC14**: Given an observed adapter with no usable guest report, hardware status remains populated and hardware readiness can be true while guest information is unknown. A VM can bootstrap and power on without waiting for Tools to run.
15. **AC15**: Given removed hardware, a reused device key with a different MAC, duplicate/ambiguous guest reports, or unavailable Tools, stale guest data does not populate the current interface or primary addresses. The condition explains the failure or uncertainty. Services and default-target probes do not keep consuming withdrawn primary addresses.
16. **AC16**: Given an in-place attachment change preserving key and MAC, the old guest report is invalidated. Operator restart and snapshot recovery do not erase that uncertainty. A new attachment is not declared guest-synchronized merely because cached global and per-interface IPs agree. Repeated reads or elapsed time alone do not clear the uncertainty.
17. **AC17**: Given old-version clients, status patches, and conversion round trips, the new conditions and hardware fields obey an explicit API-version contract. Compatibility tests prevent information from being silently erased, wrongly attributed, or restored over fresher status.
18. **AC18**: Given a provider migration requiring removal of old attachment identity, observed hardware no longer carries the old external identity after success; missing required provider addressing remains pending rather than creating a wrongly addressed adapter. Existing adapter type, placement, and unrelated tuning survive an edit.
19. **AC19**: Given cancellation or superseding replacement, or an operator restart after disconnect, the latest desired attachment is revalidated and automatically connected when ready, with no stale-resource deletion. Reconciliation does not depend on process-local state retained between calls or saved previous connection settings. A concurrent VM change is not overwritten by a stale device edit.
20. **AC20**: Given a removed interface that cannot yet be detached, users can still identify the retiring adapter and required action in status. Given unused-resource cleanup failure, hardware readiness remains accurate and cleanup feedback identifies the affected resource.
21. **AC21**: Given hardware-ready hot-plug with no guest configuration agent, status explains that guest configuration is still required and exposes current resolved settings. Unknown guest validity does not report end-to-end connectivity success. A documented and tested recovery procedure exists for stale data that cannot refresh live.
22. **AC22**: Given old/new provider allocations sharing a network or preventing overlap, replacement either completes through a validated handoff or reports the specific blocked dependency. It neither leaks resources through backing-only matching nor silently deletes an active allocation to break the dependency.
23. **AC23**: Given a LinuxPrep or Sysprep VM with the capability enabled, an interface addition, removal, attachment change, or change to an existing interface's declared addressing, live or powered off, does not cause customization at the next start. Status reports that the changed interface still needs guest configuration (AC21). A later change to another customization input, such as the host name, re-customizes with the current network settings. Enabling the capability on a VM whose inputs are unchanged triggers no customization.
24. **AC24**: Given a matched adapter and a different explicit supported `type`, reconciliation emits Remove then Add of the requested concrete type in one task at the same unit number, without an Edit of the removed device. Provider readiness and both operation eligibility checks precede removal; unsupported live replacement waits for power-off. A simultaneous attachment change uses the ready destination CR and connects the new card in that task. A type-only change keeps its provider CR. Fresh observation establishes convergence and a subsequent pass is a no-op, including after restart and key/MAC reuse. Guest invalidation and G15 apply.
25. **AC25**: Given an explicit supported type on a new interface, create and hot-add construct that concrete type. An omitted type retains an existing matched or class/image adapter's type and otherwise defaults to VMXNet3; clearing the field does not convert an existing card to VMXNet3. A type mismatch does not change matching or allow fallback from an exact-number miss. Destination-incompatible tuning is not copied, invalid explicit tuning is reported, and unsupported types are not silently created as VMXNet3. Capability-absent behavior remains unchanged.
